# Design

## Context

- auth-api (`proto/auth/v1/token.proto`, verified on `rixl/org-split-impl` 049bc6bc) serves `ListSignIns`, `RevokeSignIn`, `RevokeOtherSignIns` and `LogoutAll`. Each entry is a sign-in: a refresh-token family created at sign-in and rotated on every refresh, with the old token dropped. The `SignIn` message has `id`, `created_at`, `last_used_at`, `expires_at`, `auth_method`, `user_agent`, `ip`, `country` and `current`.
- auth-api `sign-ins` spec: the routes are account-scoped and work while the token's org is inactive. `RevokeOtherSignIns` fails with FAILED_PRECONDITION (gateway 400) when the token names no sign-in. `LogoutAll` also blacklists the caller's access token. An unknown or foreign ID returns NOT_FOUND (404).
- The gateway checks revocation with the access token's `sign_in_id` claim. Every access token carries it after the cutover, so the SDK has no legacy-token case.
- The SDK client is generated by hey-api from `https://raw.githubusercontent.com/rixlhq/openapi/refs/heads/main/openapi.yaml` (`vite.config.ts`). That document doesn't contain these routes today.
- `logout()` (`src/auth/auth/logout.ts`) is the model for clearing local state: `removeTokens()`, `clearSocialConnectAttempts()`, `announceLogout()`, in a `finally`.
- Wrappers follow `src/auth/passkey.ts`: `apiCall(...)` around a generated call with `throwOnError: true`, snake_case fields copied from the wire type with defaults.
- The SDK decodes access tokens with `jose` `decodeJwt` (`src/auth/utils/jwt.ts`).

## Goals / Non-Goals

**Goals:** expose the four auth-api routes through typed, hand-written SDK functions, with consistent device labels.

**Non-Goals:** backend changes, UI, device naming.

## Decisions

### Name the SDK functions after the auth-api RPCs

- **Chosen:** `listSignIns`, `revokeSignIn`, `revokeOtherSignIns`, `logoutAll`, and the type `SignIn`, in `src/auth/sign-ins/`. The SDK is an API layer, so it uses the backend's resource name, as `listPasskeys` and `logout` do. "Signed-in devices" is UI copy and lives in the dashboard.
- **Alternatives considered:** device names in the SDK, rejected because a sign-in is not a device (two browsers on one machine are two sign-ins) and two names for one resource across SDK and API make every bug report ambiguous.
- **Dropped:** the first draft's `listSignedInDevices`, `signOutDevice`, `signOutOtherDevices` and `signOutEverywhere`, and the module path `src/auth/devices/`. Replaced by the names above. The prepared parser moves to `src/auth/sign-ins/user-agent.ts` unchanged.
- **Evidence:** auth-api `rename-sessions-to-sign-ins` design ("Sign-in for the refresh-token family"); `src/auth/passkey.ts` naming.

### The SDK decides "current" from the access token

- **Chosen:** `revokeSignIn(signInId)` compares `signInId` with the `sign_in_id` claim of the stored access token. On a match it clears local state after the request succeeds.
- **Alternatives considered:** taking a `SignIn` object and reading `current`, rejected because a stale list entry could be wrong after a refresh in another tab; asking the server, rejected as an extra request.
- **Dropped:** none.
- **Evidence:** auth-api `sign-ins` spec, "A sign-in is one refresh-token family" (the claim is the sign-in ID); `src/auth/utils/jwt.ts`.

### Revoking the current sign-in clears state only on success; `logoutAll` always clears

- **Chosen:** a failed `revokeSignIn` of the current sign-in rejects and keeps the user signed in, so they can retry. `logoutAll()` clears local state in a `finally`, like `logout()`, because the user asked to be signed out here too.
- **Alternatives considered:** clearing on any `revokeSignIn` failure, rejected because a network error would sign the user out locally while the sign-in still exists server-side and nobody can see it to revoke it.
- **Dropped:** none.
- **Evidence:** `src/auth/auth/logout.ts`.

### No legacy-token handling

- **Chosen:** no code path for an access token without `sign_in_id`.
- **Alternatives considered:** none; the cutover revokes every token issued before `sign_in_id` existed, and auth-api and the gateway stop accepting them in the same release.
- **Dropped:** an earlier draft's scenarios for access tokens without a family ID.
- **Evidence:** auth-api `separate-organizations-from-users` design, Migration plan.

### Parse the user agent in the SDK

- **Chosen:** a minimal in-repo parser for the major browsers and OSes (`user-agent.ts`), for display only.
- **Alternatives considered:** `ua-parser-js`, not needed once the in-repo parser covered the cases within budget; parsing in auth-api, rejected because it would change the API for a display concern.
- **Dropped:** none.
- **Evidence:** tasks 2.2 measurements (41 parser tests, 32.23 kB Brotli against 32.9 kB).

### Fix the OpenAPI pipeline instead of hand-writing HTTP calls

- **Chosen:** wait for the generated client. Generated code is never hand-edited.
- **Alternatives considered:** hand-rolled fetch calls, rejected because they bypass auth headers, refresh and error handling.
- **Dropped:** none.
- **Evidence:** `AGENTS.md` repository layout (`src/generated/` is generated).

## Risks / Trade-offs

- **[Risk]** The OpenAPI document lives in another repo. → Task 1.1 tracks it; the SDK work is blocked until the regenerated client contains the routes.
- **[Risk]** Revoking the current sign-in while other tabs are open. → Reuse `announceLogout()` so every tab clears state.
