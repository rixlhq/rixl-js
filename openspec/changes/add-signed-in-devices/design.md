# Design

## Context

- auth-api (`proto/auth/v1/token.proto`) serves `ListSignIns`, `RevokeSignIn`, `RevokeOtherSignIns` and `LogoutAll` after its `rename-sessions-to-sign-ins` change. Each entry is a sign-in: a refresh-token family created at sign-in and rotated on every refresh, with the old token dropped.
- The gateway checks revocation with the access token's `sign_in_id` claim. Every access token carries it: the org-split cutover revokes all earlier tokens, so the SDK has no legacy-token case.
- The SDK client is generated by hey-api from `https://raw.githubusercontent.com/rixlhq/openapi/refs/heads/main/openapi.yaml` (`vite.config.ts`). That document doesn't contain these routes today, and the gateway's `docs/swagger.json` lacks them too.
- `logout()` (`src/auth/auth/logout.ts`) is the model for clearing local state: `removeTokens()`, `clearSocialConnectAttempts()`, `announceLogout()`.

## Goals / Non-Goals

**Goals:** expose the existing auth-api device endpoints through typed, hand-written SDK functions, with consistent device labels.

**Non-Goals:** backend changes, UI, device naming.

## Decisions

### Name them "devices" in the SDK, keep the backend names

The backend resource is a sign-in (one refresh-token family). Users think of it as a device or browser they're signed in on, as on Google's "Your devices". So the public SDK names use devices, and the generated layer keeps the backend's sign-in names.

### No legacy-token handling

An earlier draft had scenarios for access tokens without a family ID. Dropped: the cutover revokes every token issued before `sign_in_id` existed, and auth-api and the gateway stop accepting them in the same release.

### Parse the user agent in the SDK

Parse with a small, maintained parser (for example `ua-parser-js`, if its license and size fit the bundle budget; otherwise a minimal in-repo parser for the major browsers and OSes). Parsing in the SDK keeps every client consistent without a backend change. Alternative rejected: parsing in auth-api would change the API for a display concern.

### Fix the OpenAPI pipeline instead of hand-writing HTTP calls

The SDK convention is generated transport plus hand-written wrappers. Hand-rolled fetch calls would bypass auth headers, refresh and error handling. If the published document can't be updated in this change, the task stays open and blocked. Generated code is never hand-edited.

## Risks / Trade-offs

- **[Risk]** The OpenAPI document lives in another repo. → Tasks 1.x cover it; the SDK work is blocked until the regenerated client contains the routes.
- **[Risk]** Revoking the current device while other tabs are open. → Reuse `announceLogout()` so every tab clears state.
